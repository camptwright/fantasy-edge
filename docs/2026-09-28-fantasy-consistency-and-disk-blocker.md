# Fantasy consistency repair and deployment blocker

**Update: disk-capacity blocker resolved after explicit user approval; see recovery verification below.**

September 28 evening, America/Chicago (September 29 UTC).

## Implemented

- API-owned fantasy calculations now start a read-only repeatable-read transaction before checkpoint lookup or generation. A fallback cannot mix database input versions across its multiple queries while ingestion commits changes. Each new calculation still gets a fresh snapshot.
- Operations displays process-cumulative checkpoint hits/misses, custom requests, completed builds and failed builds. Counters use fixed labels, not league/player identifiers. Shared concurrent callers count as one calculation; custom requests are excluded from the checkpoint hit rate. These counters reset with the API process and are included in its next durable monitoring observation.
- Isolated PostgreSQL tests prove that an intervening source commit is invisible inside a calculation but visible to the next calculation. Cache-hit/error counters and read-only isolation are also covered.
- **715 Python tests passed**, one skipped, 20 live-network tests deselected; **13 dashboard tests passed**. Production builds/type checks and whitespace checks passed.

## Deployment verification interrupted by disk exhaustion

Backend and dashboard images were rebuilt and replaced. The local preview rollback was retained as `fantasy-edge-grading-preview-before-20260929T012751288326`.

Both Celery workers failed to start with `OSError: [Errno 28] No space left on device` while creating `/tmp/pymp-*`. The Docker filesystem reported 59 GiB total, 56 GiB used, and **zero bytes available to non-root processes**. Exact inspection showed approximately 3.11 GB free including reserved blocks. This arose during deployment verification; repeated builds contribute storage pressure. It is not a successful full deployment health check.

Read-only inventory showed about 42 GB in Docker volumes and 12 GB of build cache (shared sizes cannot simply be added). Targeted removal of explicitly inventoried build intermediates reclaimed a small amount, but no usable capacity was restored. Attempts to reclaim older cache returned zero further bytes. No image, rollback container, volume, database or raw evidence was deleted. Removed cache can be regenerated by building again.

The API remains reachable: `/health` returned 200 and a real fantasy decision-model fallback returned 200 in 1.72 seconds. New counters recorded one checkpoint miss and one completed generation. Background ingestion/evaluation remain unavailable while workers restart. Two-run durable monitoring verification was not completed; do not claim fresh background work from API availability alone.

This interrupts all containers on that VM, not just Fantasy Edge, and therefore awaits user approval. No disk expansion or VM restart was performed.

After authorized recovery: verify both workers, database health, forecast freshness, on-demand and cached fantasy paths, two successive monitoring runs, deployment provenance, and app pages. ## Approved recovery — September 28, approximately 21:09 CDT

Before this operation, the containers had already recovered and the 60 GiB Docker disk showed 5.5 GiB available. The cause of that intervening recovery was not established; it was not attributed to this resize.

With explicit user approval, gracefully stopped Colima and restarted its existing default VM with `--disk 100 --cpu 4 --memory 8 --activate=false`. No VM deletion, volume removal, or database recreation occurred. Colima reports **100 GiB** allocated; the mounted filesystem reports **99 GiB total, 44 GiB available, 54% used**. CPU and memory remain unchanged.

- All ten previously running containers returned, including the tunnel and local model proxy. PostgreSQL and Redis report healthy; both Celery workers answer ping.
- API/database health returned 200. Cached fantasy decision models returned 200 in 0.353s with `background_checkpoint`; a bounded custom player-values request returned 200 in 1.715s.
- Grading was fresh and production capture was current (latest captured 180 records before restart). This verifies freshness and worker availability, not a claim that every provider has been polled again since restart.
- Two successive monitoring task executions succeeded on fresh event loops. First correctly recorded the API process change; second had no alerts. Persisted metrics showed one checkpoint hit, one custom request and one completed build.
- Backend release verification: all four services match 242 checked files and pinned dependencies. Both frontend deployments match 59 source inputs and 148 artifacts; build ID `qdbPijoMD10HqFqvjqu0Q`.
- Fantasy, Best Bets, Calibration, Experimental and Operations returned HTTP 200. Fantasy completed in 0.299s in the measured request.

No further data/cache deletion occurred during this approved resize. Disk-pressure monitoring and pre-build capacity checks remain the next preventive work; the broader model-evidence and commit-cleanup limitations remain open.
